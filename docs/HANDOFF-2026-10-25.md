## 3. What this continuation implemented

### Controller, workers and independent bindings

- [runtime/workers.py](../runtime/workers.py): persistent binding/worker registry,
  target validation, SSH installation/control, stopped-definition save semantics,
  start/stop/delete/enrollment actions, cached concurrent telemetry.
- [runtime/node_agent.py](../runtime/node_agent.py): SSH-controlled Linux worker
  with no public management API or persistent control daemon; starts independent
  bridge/tunnel processes, checks PID birth times, rejects occupied ports, protects
  existing/mixed Tailscale handlers, reports process and host metrics.
- [runtime/worker_bridge.py](../runtime/worker_bridge.py): per-binding HTTP/stdio
  MCP edge using the existing OAuth authorization server, separate auth store and
  signing identity, required `loopback:exec` scope, tools/resources/prompts proxying,
  and counted authenticated MCP body traffic. Incoming credentials/cookies are
  stripped from HTTP upstream requests; an optional target-local upstream token
  file is separate from the caller's credential.
- Wired the subsystem into bootstrap/context, the admin fabric API and topology.
  The worker exposes only the configured upstream; installing it does not silently
  add shell/filesystem tools. See [WORKERS.md](WORKERS.md) for the actual workflow.
- Each binding has its own process, port, OAuth database, signing key and enrollment.
  Save does not expose a service; Start is explicit. The desktop machine token is
  not accepted as worker authentication.

### SSH, isolation and routes

- Added `use_ssh_config` and the dashboard checkbox to preserve the user's existing
  SSH alias host, user and port. Explicit `-p 22` had overridden working aliases
  and initially prevented all remote installs. Fixing this enabled deployment.
- Direct MagicDNS TCP/22 attempts timed out. `tailscale ssh` required an interactive
  check. We did not weaken tailnet policy; the existing SSH aliases worked.
- Added protection to both worker and legacy gateway Tailscale management: refuse
  occupied HTTPS ports, never reset the tailnet, remove only an exact owned root
  proxy, and refuse cleanup if handlers were externally changed/mixed.
- No new public VM tunnel/DNS route was provisioned. No existing Cloudflare
  connector configuration or RotoXY listener was rewritten by this continuation.

### Dashboard and branding

- Reworked the vanilla-JS/CSS dashboard using a light sidebar/content layout,

- Added Services & tunnels editing/control, worker selection, transport/upstream
  fields, exposure choices, enrollment entry points and stopped/running states.
- Added worker/host telemetry rings and service-hosting topology relationships.

- Fixed the mobile hamburger whose flex gaps/margins collapsed its bars.
- Main files: [app.js](../runtime/static/app.js), [app.css](../runtime/static/app.css),
  [index.html](../runtime/static/index.html), [topology.js](../runtime/static/topology.js)

### Startup regression and repair

The upgrade left the owner's existing standalone connector outside the new
startup management. The CLI also checked only local health: if the server was
already up and the connector stopped, the server-start hook did not run again,
and `loopback up` could still print success. The owner correctly called this a
regression. Initial upgrade validation did not catch that routine startup failure.

PR #6 repairs the code, but is **not yet installed on the desktop**:

- Up/start and restart explicitly reconcile configured Cloudflare ingress even if
  the gateway is already running. Failure returns nonzero and names the log command.
- Upgrade verification checks ingress startup too, so a launch failure cannot be
  hidden by local `/healthz` success.
- `up --cloudflare-config PATH --host HOST` imports an existing YAML path once;
  it is persisted and roundtripped through legacy env migration. The YAML, tunnel,
  credentials and DNS are not rewritten. Later starts need only `loopback up`.
- On Linux, a same-user connector with the exact saved config/token-file argument
  is reused rather than duplicated; other connectors are left alone.
- Diagnostics no longer demand an origin login certificate simply to run an
  already-configured tunnel. See [UPGRADE.md](UPGRADE.md).

   Cloudflare/Funnel endpoint was deployed. ChatGPT/Perplexity browser OAuth was
   not tested end-to-end. Do not turn these into completed checklist items.
4. **Cloudflare provisioning is manual today.** Each binding needs its own
   target-local token file, configured hostname and origin. The dashboard does not
   create Cloudflare tunnels/DNS or distribute secret tokens automatically.
5. **Workers are Linux-only today.** They use `/proc` for process identity and
   metrics. The main gateway retains broader platform support; do not infer remote
   workers have been tested on macOS, Windows or Android.
6. **No automatic worker/service recovery after VM reboot.** Processes survive a
   controller restart, but a rebooted VM needs services restarted from the dashboard.
   User-level systemd/supervision is potential future work, not already delivered.
7. **Stdio support is partial MCP proxying.** Tools/resources/prompts are forwarded;
   server-initiated sampling, elicitation and subscription forwarding are not.
   Upstream sessions are shared within one binding; per-client upstream isolation
   is not implemented.
8. **Metrics have explicit semantics.** CPU is normalized against total host CPU
   capacity; memory is summed process RSS (shared pages can be counted more than
   once). MCP throughput counts authenticated body bytes, not TLS/headers/OAuth or
   all network traffic. Host non-loopback interface sums can double-count stacked
   virtual interfaces. First rate/CPU samples are unknown. Read WORKERS.md.
9. **No provider-limit bypass.** Funnel supports HTTPS ports 443/8443/10000 per
   host. Ports, OS resources and provider quotas still bound practical capacity.
10. **Earlier release limitations remain.** The inherited CI/release replacements
    live under `.github/workflows-proposed/` because the earlier pushing credential
    lacked workflow permission. They were not adopted here. npm publishing and a
    v4 release/tag were not performed. Check provider state before any release.
